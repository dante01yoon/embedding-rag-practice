# 66. 고르는 기준과 길 하나 더

> C3 · 문서가 수십만 개일 때 — 끌어와서 grep · 수업 66 / 66 · [전체 목록](../../README.md#수업-목록)

## 이 수업에서 하는 것

- 우리 자료에서 통째로 뒤지기는 틀리지 않지만 문서가 늘면 느려졌고, 검색기가 후보 문서를 날라 주면 정답을 지키면서 빨라졌어요. 검색기는 사라지지 않고 후보를 추리는 일로 역할이 바뀌어요.
- 무엇을 고를지는 find 한 번의 시간이 먼저 기준이에요. 여기에 얼마나 빨리 답해야 하는지를 함께 봐요.
- 「한 번에 답하기 → 끌어와서 뒤지기」 라우터는 정답이 같고 비용은 약 5퍼센트 많았어요. 이득은 1단계에서 끝난 쉬운 질문의 응답 시간이에요.

## 실행

먼저 문서 묶음을 받고 색인을 만듭니다 (이미 했다면 건너뜁니다): [C3 자료 받기](../../c3/README.md)

```bash
uv run python c3/build_index.py 10k
```

수업 명령:

```bash
uv run python c3/router.py q01 10k    # 쉬운 문항 · 기증 수목 수
uv run python c3/router.py h05 10k    # 어려운 문항 · 2009년 4월 월간 타율
```

저장소 맨 위 폴더에서 실행합니다.

- **OpenRouter 키 필요.** 모델을 부릅니다. 이 두 문항은 하나에 0.01달러 안쪽입니다(영상에서 `q01` 0.0006달러, `h05` 0.0072달러).
- 영상에서는 약 65만 개 전체 묶음으로 실행했습니다(`python c3/router.py q01 all`). 전체 묶음은 받지 않으므로 끝에 받은 묶음 이름 `10k`를 적습니다. 이름을 빼면 전체 묶음(`all`)을 찾습니다.
- 영상의 결과: `q01`은 「한 번에 답하기」에서 바로 끝나 631그루(4.5초). `h05`는 1단계가 모름이라고 답해 「끌어와서 뒤지기(answered)」로 넘어가 4할 2푼 3리(18.3초). 1만 개 묶음에서는 시간과 경로가 다를 수 있습니다.

21문항 전체로 넓힌 강사 기록은 키 없이 볼 수 있습니다. 끝부분의 「넘기기」 표를 보세요.

```bash
uv run python c3/report.py
```

## 과제

내 폴더 하나를 골라 검색 속도를 재 보세요. 코드 저장소나 노트 폴더가 좋고, 없으면 쿠버네티스 문서 폴더(`k8s/ko`)를 써요. `bench.py`의 첫 인자로 그 폴더를, 그 뒤에 찾을 낱말을 넘기면 그 폴더 하나에서 찾는 시간을 재 줘요. 그리고 오늘 배운 기준 셋 가운데 어느 칸에 속하는지 적어 보세요.

```bash
uv run python c3/bench.py <내 폴더> <낱말>
```

모델을 부르지 않으니 **OpenRouter 키가 필요 없고** 비용도 들지 않습니다. `rg`(ripgrep)가 필요합니다(`rg --version`으로 확인).

## 풀이

<details><summary>풀이 보기</summary>

쿠버네티스 한국어 문서 폴더를 예로 풀어요. 이 폴더에는 문서 파일이 모두 157개 들어 있어요.

```bash
uv run python c3/bench.py k8s/ko 파드
```

「파드」가 든 파일 135개를 찾는 데 0.02초가 걸렸어요(시간은 기기마다 조금 다릅니다).

오늘 세운 기준 셋은 이래요.

1. 문서가 10만 개 안쪽이면 통째로 뒤지기. 색인을 만들 필요가 없고 21문항을 모두 맞혔어요.
2. find 한 번이 몇 초를 넘기면 끌어와서 뒤지기. 약 65만 개에서 정답을 지키면서 시간이 5분의 1로 줄었어요.
3. 몇 초 안에 답이 나와야 하는 쉬운 단답이면 한 번에 답하기. 대신 어려운 문항은 하나도 풀지 못해요.

find 한 번의 시간이 몇 초보다 훨씬 짧으니 기준 첫째 칸이에요. 바로 통째로 뒤지기를 쓰면 되는 구간이에요. 에이전트 검색 수업에서 색인 없이 grep을 쓰는 도구로 충분했던 이유예요.

기준은 문서 수가 아니라 find 한 번의 시간으로 잡길 추천해요. 기기마다 속도가 다르니 `bench.py`로 재 보고 고르면 돼요.
